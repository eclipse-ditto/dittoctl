# How to contribute to dittoctl

Thanks for considering a contribution to dittoctl, the command line tool for
[Eclipse Ditto](https://eclipse.dev/ditto/). This page explains the legal requirements, the rules that keep the
code base clean, and how to get a change merged.

## Legal requirements

dittoctl is part of the Eclipse Ditto project and follows the
[Eclipse Foundation Development Process](https://www.eclipse.org/projects/dev_process/). Before we can accept
your contribution:

* Create an [Eclipse Foundation account](https://accounts.eclipse.org/user/register) and sign the
  [Eclipse Contributor Agreement (ECA)](https://www.eclipse.org/legal/eca/).
* Add your GitHub username to your Eclipse Foundation account.
* Commit with the email address of your Eclipse Foundation account. The ECA check on each pull request verifies
  that every commit author has signed the ECA.

By contributing, you agree that your contribution is licensed under the
[Eclipse Public License 2.0](LICENSE).

## Clean-room rules

dittoctl is implemented only from public sources. This keeps the provenance of every line clear:

* Use only public sources: the [Ditto documentation](https://eclipse.dev/ditto/), Ditto's OpenAPI specification
  (`documentation/src/main/resources/openapi/ditto-api-2.yml` in
  [eclipse-ditto/ditto](https://github.com/eclipse-ditto/ditto)), and the relevant RFCs (e.g. 7396 merge patch,
  7636 PKCE, 8628 device authorization grant).
* Don't copy code, tests, fixtures, templates or documentation from other tools, including internal tools of your
  employer, unless their license allows it and the origin is stated in the pull request. Ideas and features may be
  taken over, code may not.
* Use synthetic test data only, in made-up namespaces such as `org.example`. Never commit real thing ids, policy
  ids, customer namespaces, hostnames, tokens or other data from a real Ditto installation, not even in comments,
  examples or commit messages.

## Before you start

* **Create an issue first** in [eclipse-ditto/dittoctl](https://github.com/eclipse-ditto/dittoctl/issues) for new
  features and non-trivial bug fixes, so that the approach can be discussed before much work goes into it. Small
  bug fixes and maintenance changes (documentation, build, tooling) don't need an issue; explain the change in the
  pull request instead.
* **Keep pull requests small**, well below 1,000 changed lines. Larger contributions trigger an IP review by the
  Eclipse Foundation. Split bigger changes into several pull requests that build on each other.
* **Open pull requests early**, as drafts while they aren't ready for review.

## Development setup

dittoctl needs Python 3.11 or newer.

```shell
python3 -m venv .venv
.venv/bin/pip install --upgrade pip            # pip 25.1+ for dependency groups
.venv/bin/pip install -e . --group dev
```

Before you push, run:

```shell
.venv/bin/pytest
.venv/bin/ruff check src tests && .venv/bin/ruff format --check src tests
.venv/bin/python scripts/gen_reference.py      # after changing commands or help texts (a test checks it)
```

CI runs the same checks; the tests run on Linux, macOS and Windows with Python 3.11 to 3.14.

## Code guidelines

* Formatting and linting: [ruff](https://docs.astral.sh/ruff/) with a line length of 120, as configured in
  `pyproject.toml`.
* `dittoctl.core` is a library: it never prints, it returns data or raises exceptions. The command line layer in
  `dittoctl.cli` parses options, calls `core` and renders the result.
* Every command and every option has a help text; `docs/reference.md` is generated from them. Write help texts so
  that people and LLM agents can use a command correctly without reading the code.
* Writes must stay safe: keep `--dry-run`, the `--max-affected` limit, the confirmation of protected contexts and
  Ditto's conditional headers working for every command that changes data.
* Add unit tests for every change (pytest, with [respx](https://lundberg.github.io/respx/) to mock Ditto's HTTP
  API).
* Use descriptive commit messages that explain why a change was made.

## Contributions created with generative AI

Content created with the assistance of an AI is welcome, under the Eclipse Foundation's
[Generative AI Usage Guidelines](https://www.eclipse.org/projects/handbook/#genai):

* You are responsible for the content: review and test it like your own, and only contribute what you understand
  and are willing to support.
* Disclose the use of AI: if you would give a human credit for the contribution, give the AI credit. Use the
  header with the AI disclosure above for source files that are largely AI-generated, naming the assistant you
  used.
* Name the AI assistant in an `Assisted-by:` trailer of the commit message, e.g.
  `Assisted-by: Anthropic Claude Opus 5.5 (claude-opus-5-5)`.
* Make sure your use of the AI platform is consistent with its terms of use and with your employer's policy, and
  don't put confidential information or personal data into its prompts.

## Submitting a pull request

1. Fork the repository and create a branch for your change.
2. Make the change, with tests and updated documentation (README, generated reference).
3. Push the branch to your fork and open a pull request against `main`.
4. Don't use that branch for other work while the pull request is open.

The project-wide rules of Eclipse Ditto apply as well, for example for approving and merging pull requests: see
[Ditto's CONTRIBUTING.md](https://github.com/eclipse-ditto/ditto/blob/master/CONTRIBUTING.md).

## Code of conduct and security

Please follow the [Code of Conduct](CODE_OF_CONDUCT.md). Report vulnerabilities as described in
[SECURITY.md](SECURITY.md), never in public issues.
